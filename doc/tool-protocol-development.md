# Adding a native tool protocol

Native tool support is a security and correctness boundary. Add a protocol only
when an immutable template fixture and tokenizer behavior demonstrate a stable,
constrainable wire format. A model family, repository name, or example output is
not sufficient evidence.

## Capture evidence

Add the exact selected template body under
`safemlx-lm/tests/fixtures/chat_templates/`. Record its authoritative source and
immutable source identifier in the test data or fixture name, and preserve all
meaningful whitespace. When the source lacks a final line feed, document how
the signature test removes the repository file terminator.

Add rendering cases for:

- an ordinary system/user/assistant conversation;
- tool definitions and tool results;
- one and multiple calls;
- reasoning or thinking controls where present;
- generation-prompt boundaries; and
- malformed or ambiguous output that must fail.

Signatures protect the evidence, but runtime selection must never depend on a
whole-template hash.

## Recognize behavior

Recognition belongs in the chat-protocol layer. It should verify rendered
output and required tokenizer properties, including distinct atomic special
tokens. Keep these capabilities independent:

- ordinary chat rendering;
- reasoning extraction;
- tool-definition rendering;
- tool-output parsing; and
- constrained tool-input generation.

Return no native-tool capability if any required behavior is ambiguous. Do not
fall back to architecture or model metadata.

## Prefer a declarative format

Use the declarative dialect machinery when the protocol can be expressed as
fixed wrappers around a JSON object, JSON list, named JSON arguments, or another
supported structural form. Parameterize delimiters, field names, call joining,
and reasoning channels instead of copying a parser for one checkpoint.

For each declarative extension, test:

- rendering and parsing round trips;
- incremental token and byte boundaries;
- valid and invalid function names;
- parallel-call limits;
- stop overlap and incomplete calls;
- nested supported schemas; and
- rejection of unsupported schema features.

Two templates should share a protocol identity only when their observable
rendered and generated byte behavior is equivalent.

## Add a custom dialect only when required

A stateful custom dialect is appropriate for behavior that the declarative
formats cannot model safely, such as channel transitions, recipient metadata,
structural tokens, or non-JSON literal syntax.

The dialect still has to expose the common semantic contract:

- incremental reasoning and visible-text deltas;
- indexed tool-call start, argument, and end events;
- grammar-complete detection;
- deterministic clone and discard behavior for speculative generation; and
- a precise stop and error policy.

Keep wire spellings and parser state private. Public application code should
depend only on `PreparedChat`, capability reports, semantic events, and finish
reasons.

## Validate the complete path

Tests should cover preparation, tokenizer analysis, constraints, ordinary and
MTP generation, cancellation, malformed output, and event ordering. Include a
checkpoint-backed ignored test only when fixture-level behavior cannot prove a
required property; it must use a caller-supplied local path and must never
download a checkpoint.

Before accepting support, pass the structural backend report through
`inspect_text_model` with the same request in `TextInspectionOptions`, verify
that unsupported templates remain ordinary-chat-only, and ensure raw
generation does not inherit a native-tool capability.
